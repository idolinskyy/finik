# Правила проекту «Фінік»

Стандарти для змін у коді. Фінік — десктопна бухгалтерія (C++17 / Qt 6 / SQLite) для МСБ в Україні.

---

## 1. Інженерні стандарти

1. **Стек**: C++17 / Qt6.
2. **Архітектурний розподіл**:
   - Ядро предметної області (`fin_core`) повністю відокремлене від графічного інтерфейсу (жодних `QWidget`, `QAction` чи UI-залежностей у `fin_core`).
   - UI (`fin_ui` / `Finik`) — тонкий шар адаптерів та представлення.
   - Тести покривають доменні інваріанти, правила проведення, розрахунки та цілісність даних.
3. **Робота з грошима та величинами**:
   - **Гроші**: виключно цілочисельні копійки (`int64_t cents`). Використання типів з плаваючою крапкою (`double`, `float`) для сум суворо заборонено. Обов'язкова перевірка на переповнення.
   - **Кількість товару/МШП**: цілочисельні міліодиниці (3 знаки після коми, 1 шт = 1000 міліодиниць), ніколи не `double`.
4. **Обробка помилок**:
   - Всі операції API повертають `fin::Status` або `fin::Result<T>`.
   - Жодних проковтнутих SQL-помилок або порожніх блоків `catch`.
5. **База даних (SQLite)**:
   - `PRAGMA foreign_keys = ON;` для кожного з'єднання.
   - Транзакції з модифікацією даних використовують `BEGIN IMMEDIATE`.
   - Міграції схеми виконуються виключно через механізм `schema_migrations`.
6. **Незмінність та проведення**:
   - Проведені документи є незмінними (immutable).
   - Записи в Головній книзі (`ledger_entries`) та складські рухи (`inventory_movements`) створюються та видаляються виключно через `PostingEngine` (post/unpost).
7. **Управління ресурсами та стиль C++**:
   - Суворий RAII всюди. Жодного ручного виклику `delete` (використовувати `std::unique_ptr`, `std::shared_ptr` або батьківське володіння Qt для `QObject`).
   - `const`-коректність, `enum class`, строго типізовані ідентифікатори (Strong IDs).
   - Принцип "include what you use". Компіляція з прапорцями `-Wall -Wextra -Wpedantic`.
8. **Мовні стандарти**:
   - Ідентифікатори в коді (класи, методи, змінні) — англійською мовою.
   - Інтерфейс користувача (тексти, мітки, повідомлення, друковані форми) — грамотною українською мовою.
   - Коментарі до коду — професійні, змістовні, українською мовою.
9. **Конфігуратор**: Не додавати конфігуратор у стилі 1С, якщо немає прямої вказівки.

---

## 2. Стандарти коментування коду

1. **Цільова аудиторія коментарів**: Коментарі призначені для розробників, щоб швидко зрозуміти архітектуру, бізнес-логіку та бухгалтерські правила.
2. **Змістовність**:
   - Не пояснювати очевидні речі та синтаксис мови C++ (наприклад, не писати «конструктор за замовчуванням» або «повертає значення поля»).
   - Пояснювати **ЧОМУ** реалізовано саме так (контекст українського бухобліку, ПСБО, ПКУ, логіка першої події, порядок закриття рахунків, інваріанти цілісності).
3. **Термінологія**: Використовувати точну українську економічну та бухгалтерську термінологію (сальдо, оборот, кореспонденція, дебет, кредит, середньозважена собівартість, нарахування амортизації, податковий кредит/зобов'язання, ЄРПН тощо).

## 3. Облікове ядро (Accounting Core Model)

1. **Проведення**: Один рядок у Головній книзі (`ledger_entries`) відповідає одній кореспонденції: рахунок дебету, рахунок кредиту, сума в копійках, документ-підстава, дата.
2. **Рядки документів**: Чернетка операції (`document_lines`). При проведенні валідовані рядки трансформуються та записуються у `ledger_entries`.
3. **Рахунок 00**: Використовується виключно для початкових залишків. Папки плану рахунків (`is_folder = 1`) ніколи не беруть участі у проводках.
4. **Типи документів**:
   `opening_balance`, `manual`, `cash_in`, `cash_out`, `purchase`, `sale`, `service_sale`, `service_purchase`, `customer_invoice`, `bank_payment`, `sale_return`, `purchase_return`, `write_off`, `stocktake`, `period_result`, `fa_commission`, `fa_depreciation`, `fa_write_off`, `ia_commission`, `ia_depreciation`, `ia_write_off`, `ms_receipt`, `ms_issue`, `tax_invoice`, `payroll`.
5. **Основні рахунки плану рахунків**:
   - Каса: `301`, Банк: `311`, Товари: `281`, МШП: `22`
   - Розрахунки з покупцями: `361`, Розрахунки з постачальниками: `631`
   - Видані аванси: `371`, Отримані аванси: `681`
   - Дохід від реалізації товарів: `701`, Дохід від послуг: `703`, Собівартість реалізації: `902`, Інший операційний дохід: `71`, Адміністративні витрати: `92`
   - Фінансовий результат: `79`, Нерозподілений прибуток (збиток): `44`
   - Основні засоби: `104`/`105`/`109`, Знос ОЗ (контрактив): `131`, Капітальні інвестиції ОЗ: `152`
   - Нематеріальні активи: `125`/`127`, Накопичена амортизація НМА (контрактив): `133`, Капітальні інвестиції НМА: `154`
   - ПДВ: Папка `64`, Розрахунки з бюджетом: `641`, Податкові зобов'язання: `643`, Податковий кредит: `644`
   - Зарплата: Розрахунки з оплати праці: `661`, ЄСВ: `651`, ПДФО: `642`, Військовий збір: `645` (не 641); Витрати: `92`
6. **ОСВ та Картка рахунку**: Повинні збігатися за той самий період включно (`date_from`..`date_to`). Початкове сальдо обчислюється для `date < date_from`.
7. **Контрагенти**: Обов'язкові для торгових/послугових документів, повернень, рахунків, а також банківських та касових операцій за рахунками 361, 631, 371, 681.
8. **Облік запасів (281)**:
   - Рядки з 281 містять номенклатуру та кількість.
   - Списання за середньозваженою собівартістю. Сума списання розраховується в момент проведення.
9. **Закриття періоду**:
   - Дата `closed_through` блокує будь-які зміни, проведення чи розпроведення на цю дату включно.
   - Перед закриттям рахунки доходів і витрат (701, 703, 71, 902, 92, 79) повинні бути закриті на фінансовий результат (документ `period_result` → 44).
10. **Необоротні активи (ОЗ, НМА, МШП)**:
    - Облік через окремі картки/довідники.
    - Амортизація починається з місяця, наступного за введенням в експлуатацію (НП(С)БО 7, НП(С)БО 8).
    - При списанні об'єкта дораховується амортизація за поточний місяць.
11. **Податок на додану вартість (ПДВ)**:
    - Прапорець платника ПДВ (`vat_payer`) та ставка (`vat_rate_bp`, за замовчуванням 2000 = 20%).
    - Податкова накладна (`tax_invoice`) формується на підставі першої події. Проводки формуються через 643/644, а при реєстрації в ЄРПН закриваються на 641.
12. **Зарплата та кадри**:
    - Документ `payroll` раз на календарний місяць.
    - Розрахунок окладу, ЄСВ (22% / 8.41% для осіб з інвалідністю, обмеження мінбази), ПДФО (18%), Військового збору (5%).
    - Виплата через банк/касу на підставі відомості безпосередньо по рахунку 661.
13. **Електронний документообіг (ЕДО) та Банк-Клієнт**:
    - Імпорт банківських виписок у форматах CSV/XML зі створенням непроведених чернеток `bank_payment` та зіставленням за ЄДРПОУ.
    - Експорт/імпорт податкових накладних у форматі XML з контролем SHA-256 хешу.

## 4. Контроль цілісності та безпека

1. **Integrity Checker**:
   - Контроль нульового балансу (сума дебетів дорівнює сумі кредитів).
   - Відповідність складських залишків сальдо рахунку 281.
   - Відповідність залишків ОЗ, НМА, МШП відповідним субрахункам (10x, 12x, 22, 131, 133).
2. **Рольовий доступ**:
   - `admin`, `accountant`, `cashier`, `viewer`.
   - Перевірка прав реалізована на рівні репозиторіїв та сесії, а не лише приховуванням кнопок в UI.
   - Заборонено деактивувати чи понижувати права останнього активного адміністратора.
3. **Резервне копіювання та відновлення**:
   - Безпечне відновлення через поетапний механізм (`.incoming`, `.restore-pending`, копія безпеки `.before-restore`).

## 5. Локальні перевірки

Скрипт на bash + системний `clang-format`:

```bash
./scripts/check.sh            # перевірка формату src/ + tests/
./scripts/check.sh format-fix # перезапис (лише свідомо)
./scripts/check.sh test       # ./build/tests/fin_tests
./scripts/check.sh all
```

Опційний git hook (лише staged `.cpp`/`.h`):

```bash
git config core.hooksPath .githooks
```
