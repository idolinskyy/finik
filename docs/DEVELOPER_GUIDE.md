## 2. Бухгалтерія за 20 хвилин

### 2.1. Навіщо взагалі «рахунки»

Уявіть, що компанія — це набір **кишень** (готівка, рахунок у банку, товар на складі, борги покупців, борги перед постачальниками, податки, зарплата, прибуток).
Кожна кишеня має **номер** — це і є **рахунок** плану рахунків.

Рух грошей/товару ніколи не «зникає»: він **виходить з однієї кишені і заходить в іншу**. Це називається **подвійний запис**.

### 2.2. Дебет і кредит — не «плюс» і «мінус»

У програмуванні хочеться писати `balance += amount`. У бухгалтерії кожна проводка має **два боки**:

- **Дебет (Дт)** — ліва сторона.
- **Кредит (Кт)** — права сторона.

Що означає «збільшення», залежить від **типу** рахунку:

| Тип кишені | Приклади | Збільшення | Зменшення |
| ---------- | -------- | ---------- | --------- |
| Актив (те, що нам належить) | каса 301, банк 311, товар 281, борг покупця 361 | **Дебет** | Кредит |
| Пасив / зобов’язання (те, що ми винні) | борг постачальнику 631, зарплата 661, ПДВ 641 | **Кредит** | Дебет |
| Дохід | виручка 701, послуги 703 | **Кредит** | Дебет |
| Витрата | адмінвитрати 92, собівартість 902 | **Дебет** | Кредит |

**Інваріант, який Фінік ніколи не порушує:** у кожній проводці сума Дт = сума Кт. Глобально по всій Головній книзі теж Σ Дт = Σ Кт. Це перевіряє `IntegrityChecker`.

Приклад. Покупець заплатив 1000 грн на банк:

```
Дт 311  1000   (банк зріс — актив, тому дебет)
Кт 361  1000   (борг покупця зменшився — актив зменшується кредитом)
```

У коді це **один** рядок `ledger_entries` з `debit_account_id`, `credit_account_id` і `amount_cents`. Не два рядки «плюс / мінус».

### 2.3. Чернетка і проведення

- **Чернетка** (`documents.posted = 0`) — бухгалтер набрав папірець. На баланс, склад і податки **не впливає**. Лежить у `documents` + `document_lines`.
- **Проведення** (`PostingEngine::post`) — з рядків документа народжуються рядки **Головної книги** (`ledger_entries`) і, якщо треба, складські рухи (`inventory_movements`).
- **Зняття проведення** (`unpost`) — книга й склад відкочуються, документ знову чернетка.

Проведений документ **не редагують**. Спочатку `unpost`, потім правка, потім знову `post`. Якщо місяць закритий (`closed_through`) — і post, і unpost заборонені.

### 2.4. Первинний документ ≠ проводка

**Первинний документ** — те, що бухгалтер «бачить»: накладна, касовий ордер, банківська виписка.
**Проводка** — наслідок у книзі.

Один документ може дати **кілька** проводок. Продаж товару зазвичай:

1. Дт 361 Кт 701 — нарахували виручку і борг покупця.
2. Дт 902 Кт 281 — списали товар зі складу за собівартістю (не за ціною продажу!).

Ціну продажу і собівартість **не можна плутати**. Інакше «прибуток» стане кашею.

### 2.5. Що таке сальдо, оборот, ОСВ

- **Оборот** — сума рухів за період (окремо Дт, окремо Кт).
- **Сальдо** — залишок на рахунку на дату.
- **ОСВ** (оборотно-сальдова відомість) — таблиця по всіх рахунках: вхідне сальдо + обороти + вихідне сальдо. Це головний звіт, що «книги зійшлись». Код: `TrialBalanceReport` у `src/fin/reports/Reports.cpp`, UI — `src/ui/TrialBalancePage.cpp`.

### 2.6. Нормативні слова, які зустрінете в коментарях

| Слово | Що це |
| ----- | ----- |
| НП(С)БО | Національні положення бухобліку України (стандарти). НП(С)БО 7 = основні засоби, 8 = НМА, 21 = валюта. |
| ПКУ | Податковий кодекс України. |
| ПДВ | Податок на додану вартість, зазвичай 20%. |
| ЄРПН | Реєстр податкових накладних ДПС. Фінік **не підписує** XML ключем; бухгалтер несе файл у M.E.Doc / Кабінет. |
| КО-1 / КО-2 / КО-4 | Типові касові форми НБУ. |
| Інструкція НБУ № 163 | Форма платіжної інструкції (безготівка). |
| КМУ № 100 | Порядок середнього заробітку (відпускні, лікарняні). |

Фінік — **не клон 1С**. Мета: робоче місце бухгалтера МСБ на одному ПК (SQLite), а не платформа з конфігуратором.

## 3. Українські рахунки в Фініку

Коди зашиті в [`src/fin/domain/ChartCodes.h`](../src/fin/domain/ChartCodes.h) як `fin::chart::k…`.
План рахунків сіється в БД через `AccountRepository::seedChartIfEmpty()`. **Папки** (`is_folder = 1`) на кшталт «64» у проводки не потрапляють — лише кінцеві субрахунки (641, 643…).

Нижче — ментальна карта, не повний план.

### 3.1. Гроші

| Код | Константа | Людською |
| --- | --------- | -------- |
| 301 | `kCash` | Готівка в касі |
| 311 | `kBank` | Поточний рахунок у гривні |
| 302 / 312 | `kForeignCash` / `kForeignBank` | Те саме в валюті |

Каса завжди «з одного боку» ордера: ПКО дебетує 301, ВКО кредитує 301. Банк — так само з 311, напрямок задає форма (`BankDocumentDialog`).

### 3.2. Товар і виробництво

| Код | Константа | Людською |
| --- | --------- | -------- |
| 281 | `kGoods` | Товари на складі (облік за **середньозваженою**) |
| 201 / 202 / 203 | сировина / комплектуючі / паливо | Матеріали |
| 231 | `kProduction` | «Калькуляція» — витрати на незавершене виробництво |
| 26 | `kFinishedGoods` | Готова продукція |
| 22 | `kLowValue` | МШП (степлер, спецодяг…) |

### 3.3. Хто кому винен

| Код | Константа | Людською |
| --- | --------- | -------- |
| 361 | `kCustomers` | Покупець нам винен (дебіторка) |
| 631 | `kSuppliers` | Ми винні постачальнику (кредиторка) |
| 371 | `kAdvancesIssued` | Ми вже заплатили постачальнику наперед |
| 681 | `kAdvancesReceived` | Покупець уже заплатив нам наперед |
| 3721 | `kAccountablePersonsUah` | Працівник узяв гроші «під звіт» |

**Аванс ≠ борг за вже відвантажене.** Якщо покупець платить до накладної — це 681, не 361. При відвантаженні рушій **заліковує** аванс: шматок 681 перетворюється на 361 (`AdvanceOffset`). Не пишіть цей залік вручну в UI — його додає `applyAdvanceOffset` під час `post`.

### 3.4. Податки і зарплата

| Код | Константа | Людською |
| --- | --------- | -------- |
| 643 | `kVatLiability` | ПДВ «ще не в бюджеті» після продажу / авансу від покупця |
| 644 | `kVatCredit` | Вхідний ПДВ «ще не підтверджений» ПН |
| 641 | `kVatBudget` | ПДВ уже після реєстрації ПН в ЄРПН |
| 642 / 645 / 651 | ПДФО / військовий збір / ЄСВ | Утримання й нарахування з зарплати |
| 661 | `kSalaryPayable` | Нарахували зарплату, ще не виплатили |

Важливо: **звичайна накладна не чіпає 641**. Лише документ «Податкова накладна». Інакше податковий облік роз’їдеться з бухгалтерським.

### 3.5. Доходи, витрати, прибуток

| Код | Константа | Людською |
| --- | --------- | -------- |
| 701 | `kRevenue` | Дохід від **товарів** (`composeSale`) |
| 703 | `kServiceRevenue` | Дохід від **послуг** (`composeServiceSale`) |
| 902 | `kCogs` | Собівартість проданих товарів |
| 92 | `kAdminExpense` | Адміністративні витрати (оренда офісу, зарплата адміну…) |
| 79 | `kFinancialResult` | Транзит закриття місяця |
| 44 | `kRetainedEarnings` | Нерозподілений прибуток (куди з’їжджає 79) |
| 00 | `kAuxiliary` | **Не справжній рахунок.** Тільки введення залишків. У щоденних документах заборонений. |

Закриття місяця (`PeriodResult`, `MonthClose.cpp`): доходи й витрати згортаються на 79, потім 79 — на 44. Після цього «виручка за місяць» на 701 обнуляється, а прибуток лишається в капіталі.

### 3.6. Рахунок 00 (введення залишків)

Коли фірма починає вести облік у Фініку, на дату старту вже є каса, товар, борги. Їх вносять документом `OpeningBalance`:

- актив: **Дт рахунок Кт 00**
- пасив: **Дт 00 Кт рахунок**

00 — штучна «протилежна кишеня», щоб подвійний запис зійшовся. Після старту 00 більше не чіпають.

## 4. Архітектура коду: де що лежить

Три цілі CMake ([`CMakeLists.txt`](../CMakeLists.txt)):

| Ціль | Що це |
| ---- | ----- |
| `fin_core` | Статична бібліотека. Уся облікова логіка. **Немає `QWidget`.** Qt Core/Sql/Network — так. |
| `Finik` | `src/main.cpp` + `src/ui/*`. Тонкі форми. |
| `fin_tests` | Catch2, `tests/`. |

Інклуди шукаються від `src/`, тобто `#include "fin/core/Money.h"`, `#include "ui/DocumentDialog.h"`.

### 4.1. Точка входу

[`src/main.cpp`](../src/main.cpp)

1. `QApplication`, локаль `uk_UA`, іконка, шрифт Inter з `help.qrc`.
2. Шлях до SQLite: `AppPaths` → `QStandardPaths::AppDataLocation` з org/app **Finik/Finik** (каталог подвійний: `~/.local/share/Finik/Finik/finik.sqlite`).
3. `applyStagedRestore` — якщо минулого разу користувач відновив бекап.
4. `LedgerSession::openFile` — PRAGMA + міграції.
5. Логін (`AuthDialogs`) або одразу `MainWindow`.

### 4.2. Сесія — єдиний фасад

[`src/fin/session/LedgerSession.h`](../src/fin/session/LedgerSession.h)

Тримає `Database` і всі репозиторії / звіти / `PostingEngine`.
UI і тести майже завжди ходять так: `session.documents()`, `session.posting().post(id)`, `session.accounts().findByCode("361")`.

Не створюйте другий `QSqlDatabase` «на око»: інший connection name зламає транзакції й `foreign_keys`.

### 4.5. База: міграції

[`src/fin/db/Database.h`](../src/fin/db/Database.h) — `kSchemaVersion = 27`.
[`src/fin/db/Database.cpp`](../src/fin/db/Database.cpp) — `migrate()`: якщо `MAX(schema_migrations.version) < N`, застосовує крок N.

Нова колонка = **новий крок**, ніколи `CREATE TABLE` на існуючій базі користувача. Свіжа `:memory:` у тестах проганяє всі кроки з нуля.

Приклад v27: `document_lines.contract_id` — договір **у рядку** (потрібно введенню залишків, де на 361/631 багато різних контрагентів).

### 4.6. Репозиторії (`db/`)

Один файл ≈ одна таблиця. Типовий контракт:

- `findById` / `list*` → `Result<T>`
- `insert` / `update` / `remove` → перевірка `Access` + валідація
- проведені документи **не** оновлює `DocumentRepository::update` (спочатку unpost)

Писати в `ledger_entries` або `inventory_movements` напряму з UI **заборонено**. Тільки `PostingEngine`.

## 5. Гроші, кількість, помилки

### 5.1. `Money` — тільки копійки

Файл: [`src/fin/core/Money.h`](../src/fin/core/Money.h)

```
100 грн 50 коп.  →  Money::fromCents(10050)
```

- Немає конструктора з `double`.
- `plus` / `minus` / `negated` / `times` (через Quantity) повертають `Result<Money>`: переповнення `int64` — помилка, не тихе wrap.
- `fromDisplayString` їсть `"1 234,56"` і `"1234.56"`.
- У звітах агрегуйте через `addTo` / `negateTo` (див. `Reports.cpp`), не через сирий `+=` на `int64`.

**Заборона:** `double` для сум, курсів «як число JSON», відсотків «на око». Ставки — **базисні пункти**: 20% ПДВ = `2000`, 18% ПДФО = `1800`.

### 5.2. `Quantity` — міліодиниці

1 шт = 1000. Три знаки після коми, без float. `quantity.times(unitPrice)` → `Result<Money>`.

### 5.3. `Result<T>` / `Status`

Файл: [`src/fin/core/Result.h`](../src/fin/core/Result.h)

Облікові помилки — **значення**, не винятки. `[[nodiscard]]`. Типові коди: `Validation`, `AlreadyPosted`, `PeriodClosed`, `Conflict`, `Overflow`.

```cpp
const Result<DocumentId> id = session.documents().insert(doc);
if (!id) {
  return id.asStatus(); // показати id.error().message
}
```

### 5.4. Strong IDs

[`src/fin/core/Ids.h`](../src/fin/core/Ids.h) — `DocumentId`, `AccountId`, `ContractId`… Це різні типи. Не передавайте `qlonglong` між шарами, окрім Qt `QVariant` на межі комбобокса.

### 5.5. Транзакції

[`src/fin/core/Transaction.h`](../src/fin/core/Transaction.h) — `BEGIN IMMEDIATE`. Проведення, міграції, insert документа з рядками — в одній транзакції. RAII: деструктор робить rollback, якщо не було `commit`.

## 6. Життя документа: чернетка → проведення → книга

```
[Форма UI]
    collect() → Document (type, header, lines)
        ↓
DocumentRepository::insert / update     → documents + document_lines
        ↓
PostingEngine::post(id)
    1. Access (роль)
    2. не CustomerInvoice / не замовлення (вони без книги)
    3. PeriodRepository::ensureDateWritable
    4. DocumentValidator::validate
    5. InventoryCosting (якщо 281/26/201…)
    6. applyAdvanceOffset (якщо продаж/купівля)
    7. extractSubcontoSet на кожне плече
    8. INSERT ledger_entries (+ inventory_movements)
    9. IntegrityChecker::verifyEngine
    10. documents.posted = 1
```

Код рушія: [`src/fin/posting/PostingEngine.cpp`](../src/fin/posting/PostingEngine.cpp).
Валідатор: [`src/fin/posting/DocumentValidator.cpp`](../src/fin/posting/DocumentValidator.cpp) — великий `switch` за `DocumentType` (кореспонденції, каса тільки 301, БО не використовує 00, обов’язкові субконто…).

`unpost` видаляє книгу й рухи, перевіряє конфлікти: не можна зняти накладну, якщо вже є проведена ПН «на підставі»; не можна зняти нарахування зарплати, якщо вже є виплата.

### 6.1. Дві таблиці, які плутають

| Таблиця | Це |
| ------- | -- |
| `document_lines` | Що бухгалтер навів. Є в чернетки. |
| `ledger_entries` | Що потрапило в ОСВ. Тільки після post. |

Звіти читають **книгу**, не чернетки. Якщо «в документі є, в ОСВ немає» — документ не проведено.

### 6.2. Поля шапки, які впливають на проводку

Див. `struct Document` у [`Document.h`](../src/fin/domain/Document.h):

Рядок (`DocumentLine`) може нести свій `counterpartyId` і `contractId` (введення залишків, переоцінка 362/632). Рушій: спочатку рядок, потім шапка (`extractSubcontoSet`).

## 7. Типи документів і хто їх збирає

Перелік `enum class DocumentType` — у `Document.h`. Рядковий ключ у БД — `documentTypeToString` (`sale`, `bank_payment`…).

**Збирати** Дт/Кт з «зручних» полів форми (товар + ціна, а не два рахунки) — робота `compose*` у [`DocumentBlueprint.cpp`](../src/fin/domain/DocumentBlueprint.cpp).
**Розібрати** проведені/збережені рядки назад у форму — `extract*`.

Це навмисно: UI не хардкодить «361/701». Якщо зміниться план — міняєте `ChartCodes` + compose.

### 7.1. Що проводиться в книгу

`requiresLedgerPosting(type) == false` для:

- `CustomerInvoice` — рахунок на оплату (оферта, не факт);
- `CustomerOrder` / `SupplierOrder` — замовлення.

Решта після `post` опиняється в `ledger_entries`.

### 7.2. Типові господарські сюжети

**Купівля товару** (`Purchase`, `composePurchase`):

```
Дт 281  сума     товар прийшов на склад
Кт 631  сума     з’явився борг перед постачальником
```

**Продаж товару** (`Sale`, `composeSale`):

```
Дт 361  ціна продажу      покупець винен
Кт 701  ціна продажу      дохід
Дт 902  собівартість      витрата
Кт 281  собівартість      товар пішов зі складу
```

Собівартість під час `post` може **перерахуватись** (`InventoryCosting::takeOutgoingCost`). У формі продажу сума 902 часто порожня/орієнтовна.

**Послуга нам** (`ServiceSale`): Дт 361 Кт **703** (не 701). Собівартості складу немає.

**Послуга від постачальника** (`ServicePurchase`): Дт 92 (або 152/154, якщо це капвкладення) Кт 631.

**ПКО** (`CashIn`, `composeCashIn`): Дт 301 Кт «звідки» (361, 681, 311…).
**ВКО** (`CashOut`): Дт «куди» Кт 301.
**Банк** (`composeBank`): один документ — або всі рядки «вхід на 311», або всі «вихід з 311». Змішувати напрямки не можна.

**Ручна операція / БО** (`Manual`): бухгалтер сам ставить Дт і Кт. Форма — `DocumentDialog`. Немає «розумної» compose-схеми, є валідатор.

**Введення залишків** (`OpeningBalance`, `composeOpening`): див. §3.6. У формі (`OpeningDocumentDialog`) на рядках 361/631/371/681 є контрагент і договір.

### 7.3. «На підставі»

`basedOnTargets` + `buildBasedOn` у тому ж `DocumentBlueprint.cpp`.
Приклади: рахунок → накладна; накладна → ПН / банк / ПКО; зарплата → ВКО або банк.

Копіюються контрагент, договір (торговий шлях), склад, рядки в новій кореспонденції. Зарплата→виплата **не** копіює контрагента (виплата на 661).

## 8. Субконто (аналітика)

ОСВ по рахунку 361 показує «усі покупці разом». Бухгалтеру треба **по Іванову окремо**. Це **субконто** — розріз аналітики на рахунку.

До 3 розрізів на рахунок (`account_subconto`, `line_no` 1..3). Види зашиті в [`Subconto.h`](../src/fin/domain/Subconto.h): контрагент, номенклатура, працівник, договір, ОЗ, НМА, МШП.

Сід схеми (спростити):

- 361 / 631 / 371 / 681: субконто 1 = контрагент (**обов’язкове**), субконто 2 = договір (**необов’язкове**, `is_required = 0`);
- 281: номенклатура обов’язкова;
- 661: працівник обов’язковий.

Якщо `is_required` і значення порожнє — `DocumentValidator` блокує проведення.

Заповнення при `post`: `PostingEngine::extractSubcontoSet` дивиться вид і тягне id з рядка або шапки документа. **Не вигадуйте** нові види в SQL без коду в цьому `if` — проведення не знатиме, звідки брати id.

UI прив’язки: `AccountPage` (ПКМ «Субконто…»). Звіт: `SubcontoTrialBalanceReport` + `SubcontoTrialBalancePage` (один вимір або **усі виміри** деревоподібно).

Де вводиться договір сьогодні:

| Форма | Де поле |
| ----- | ------- |
| Товари / послуги / замовлення | шапка (`SalePurchaseDialogs`) |
| БО | шапка (`DocumentDialog`) |
| Банк, каса | шапка |
| ПН | шапка (часто прийшло «на підставі») |
| Введення залишків | **рядок** (багато контрагентів в одному документі) |
| Імпорт виписки | колонка/тег «договір» або номер у призначенні; якщо не знайдено — порожньо, бухгалтер дописує в формі |

Друк банку підставляє `договір № … від …` у призначення (`PrintForms::bankPaymentHtml`).

Довільні види («статті витрат») — у ROADMAP, **не** в коді проведення.

## 9. ПДВ і «перша подія»

Файли: [`src/fin/domain/Vat.h`](../src/fin/domain/Vat.h), `Vat.cpp`; проведення ПН — `PostingEngine::registerTaxInvoice`; XML — `src/fin/edo/TaxInvoiceXml.cpp`; форма — `TaxInvoiceDialog`.

### 9.1. Навіщо три рахунки (641 / 643 / 644)

У податковому обліку України факт «відвантажили» і факт «зареєстрували ПН в ЄРПН» часто в **різних місяцях**.

1. Продали (або отримали аванс) → виникає зобов’язання: крутиться **643**.
2. Зареєстрували вихідну ПН → 643 іде на **641** (уже «борг бюджету»).
3. Купили → очікуваний кредит на **644**; після вхідної ПН — на **641** (зменшує борг бюджету).

Комерційна накладна в Фініку зберігає `vatRateBp` / `vatCents` на рядку, але **не проводить 641**. ПН створюють «На підставі».

### 9.2. Перша подія

ПКУ: ПДВ виникає на **ранішу** з двох подій — відвантаження або оплата.

- Продали в борг, потім оплата → ПН з накладної; оплата вже не нараховує ПДВ вдруге.
- Спочатку аванс (банк/ПКО на 681) → ПН з оплати; накладна пізніше **не дублює** зобов’язання.

Функції: `isVatAdvanceSource`, `hasPostedTaxInvoiceBasedOn`, `firstEventVat` у `Vat.cpp`. Не обходьте їх «тимчасовою» проводкою 643 з БО — роз’їдеться книга доходів і відомість ПДВ.

### 9.3. Арифметика

`vatOnNet(net, 2000)` — 20% від суми **без** ПДВ.
`vatIncludedInGross` / `netFromGross` — якщо в полі вже сума з ПДВ.
Усе в копійках, ділення цілочисельне з правилами в `Vat.cpp` (не `double`).

### 9.4. Чесно про XML декларацій

ПН XML — робочий файл для M.E.Doc. Декларації ПДВ / 4ДФ / ЄП у `DeclarationXml.cpp` — **каркас без XSD ДПС**, не файл для подачі. Не обіцяйте в UI «здати звіт».

## 10. Склад і середньозважена собівартість

Файли: [`InventoryCosting.cpp`](../src/fin/posting/InventoryCosting.cpp), `InventoryRepository`, звіт `StockReport`.

```
собівартість = (сума залишків у грн / кількість) * кількість, що йде
```

Не FIFO і не «ціна з накладної продажу». Якщо залишку бракує — помилка (від’ємний склад заборонений, якщо так налаштовано; `IntegrityChecker::rejectNegativeStock`).

Комплектація (`KitAssembly`): рядок 1 — комплект, далі компоненти; все на 281.

Кількість завжди в міліодиницях. Склад у шапці документа; рядок може перевизначити `warehouseId`.

## 12. Зарплата і кадри

### 12.1. Що відбувається при нарахуванні (спрощено)

Працівник «має отримати» оклад 10 000 грн. Держава забирає частину **з нього**, роботодавець платить ще **зверху**.

Типові ставки 2026 (базисні пункти / копійки):

- ПДФО 18% (`kPitRateBp`) — утримання з працівника → кредит **642**
- Військовий збір 5% (`kMilitaryRateBp`) → кредит **645**
- ЄСВ 22% від бази (`kSscRateBp`) — витрата роботодавця → Дт 92 Кт **651**
- ЄСВ 8.41% якщо `disabledSsc`
- ПСП (податкова соціальна пільга) зменшує базу ПДФО, якщо `hasPitBenefit` і дохід не вище порогу

Проводки нарахування (дуже схематично):

```
Дт 92     нарахування (витрата) + ЄСВ
Кт 661    «до видачі» працівнику (оклад мінус ПДФО і ВЗ)
Кт 642    ПДФО
Кт 645    ВЗ
Кт 651    ЄСВ
```

Виплата: окремий банк/ВКО **на підставі** payroll: Дт 661 Кт 311/301. Без контрагента.

### 12.2. Відпускні й лікарняні

## 19. Типові помилки новачка

1. **Писати в `ledger_entries` з діалога.** Книга роз’їдеться з `posted` і складом. Тільки `PostingEngine`.
2. **`double` для гривень або курсу НБУ.** Через місяць ОСВ не зійдеться на копійку.
3. **Проводка продажу без 902/281.** «Прибуток» стане виручкою, склад — привидом.
4. **ПДВ на 641 з накладної.** Ламає правило першої події й відомість ПДВ.
5. **Рахунок 00 у щоденному документі.** Валідатор має відшити; не обходьте.
6. **Папка 64 у рядку.** У проводках лише 641/643/644.
7. **Один `BankPayment` на всю виписку з різними контрагентами.** Модель — один контрагент на документ; імпорт уже ріже.
8. **Зміна проведеного документа update-ом.** Репозиторій не пустить; зніміть проведення.
9. **Нові норми зарплати «скопіювати 2026».** `payrollNormsForYear` має впасти, поки немає опублікованих цифр.
10. **Needle довідки розірваний переносом.** `QString::contains` не збирає два рядки HTML.
11. **Два фільтри Catch2 в одному запуску.** Часто = «No tests ran».
12. **Віджет у `fin_core`.** Шар зламано; логіку лишайте в domain/posting.
